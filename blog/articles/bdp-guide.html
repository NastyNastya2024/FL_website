Что такое Big Data Platform: принципы, архитектура, риски

Big Data Platform — on-premise инфраструктура для хранения и обработки больших данных (Hadoop, Spark, Kafka, Delta Lake): единый контур для аналитики, BI и корпоративного AI без выгрузки данных в облако.

Почему инфраструктура данных — основа цифрового бизнеса?

Краткий ответ: Контур целиком on-premise, работает на сертифицированной Astra Linux Воронеж 1.8, не содержит проприетарных компонентов и не привязывает заказчика к одному вендору.

Большинство AI-проектов, однако, ломаются не на алгоритме, а на отсутствии качественной, масштабируемой и управляемой инфраструктуры: без надёжного Data Lake, консистентных пайплайнов и среды для интерактивного анализа даже сильная модель остаётся лабораторным прототипом. Что должна уметь платформа, чтобы модель доехала до прода, — в статье по теме «AI-ready Data Platform: какая инфраструктура нужна для корпоративного AI».

«Дижитрек» (Диджи Трек, DigiTrack) Big Data Platform — ответ на этот разрыв. Это не набор утилит, а промышленная экосистема: захват в реальном времени, хранение, обработка, поставка в BI и в AI-модели. Ниже — как устроен стек, какие цифры он держит в проде и почему это фундамент корпоративного AI и аналитики.

Как устроена архитектура?

Платформа собрана из открытых компонентов, собранных и протестированных под Astra Linux. Полный доступ к исходному коду, без скрытых зависимостей и лицензионных сюрпризов. Почему открытый стек в 2026 году — вопрос суверенитета, а не вкуса архитектора, — в статье по теме «Open Source для Enterprise: почему открытый код становится вопросом цифрового суверенитета». Чеклист, по которому CTO сравнивает такие платформы, — в «Как выбрать Big Data Platform для крупного предприятия: 15 критериев оценки».

Хранение?

Краткий ответ: Ключевые варианты: Apache Hadoop 3.3.4 (custom build «Дижитрек»), HDFS, Delta Lake 2.x, PostgreSQL + Patroni.

  • Apache Hadoop 3.3.4 (custom build «Дижитрек») — основа распределённого хранилища, оптимизированная под Astra Linux и высоконагруженные контуры.
  • HDFS — отказоустойчивое хранение петабайт. В промышленном кластере — более 1 ПБ и 20+ миллионов файлов.
  • Delta Lake 2.x — ACID-транзакции, time travel, унификация потока и батча. Данные в Parquet.
  • PostgreSQL + Patroni — High Availability для Hive Metastore: автопереключение лидера, проверка через VIP.

Вычисления?

Краткий ответ: Ключевые варианты: Apache Spark 3.2.3 и 3.5.8 параллельно: унаследованные джобы и новые возможности движка без конфликта версий., Python 3.10 и 3.13, Java 1.8.0 и 11 (включая GosJava) в изолированных средах., Apache Hive 3.1.3 в режиме HA, Kyuubi.

  • Apache Spark 3.2.3 и 3.5.8 параллельно: унаследованные джобы и новые возможности движка без конфликта версий.
  • Python 3.10 и 3.13, Java 1.8.0 и 11 (включая GosJava) в изолированных средах.
  • Apache Hive 3.1.3 в режиме HA — пакетный SQL и внешние таблицы.
  • Kyuubi — JDBC/ODBC-шлюз к Tableau, Power BI, Superset и другим BI.
  • YARN — справедливое распределение ресурсов между задачами и командами.

Оркестрация и поток?

Краткий ответ: Ключевые варианты: Apache Airflow 2.8.0, Apache Kafka 2.8, Debezium Server, dbt.

  • Apache Airflow 2.8.0 — более 500 DAG ежедневной загрузки и трансформации.
  • Apache Kafka 2.8 — пик 15 000+ сообщений в секунду.
  • Debezium Server — CDC из реляционных СУБД и ClickHouse в реальном времени.
  • dbt — трансформации как код: версионирование, тесты, документация.

Стык оркестрации данных и промышленного ML — в статье по теме «MLOps начинается с DataOps: почему без управления данными нельзя построить промышленный AI».

Интерактивный анализ?

JupyterHub с ядром Toree даёт Python, Scala и R в той же среде, где потом крутится прод: исследование, визуализация, прототип модели — без выгрузки на ноутбук. BI подключается через Kyuubi; в плане на Q2 2027 — нативный коннектор к Superset и каталог OpenMetadata.

Как устроена безопасность?

Уже работает доменная аутентификация через ALD PRO и OIDC/SSO веб-интерфейсов через Keycloak. В Q4 2026 — Q1 2027: Kerberos, Apache Ranger (RBAC) и Apache Knox как единый шлюз.

Инфраструктура как код?

Все компоненты поднимаются идемпотентными Ansible-ролями из поставки: воспроизводимость, контроль версий, отсутствие дрейфа конфигурации. Это же снижает TCO внедрения — подробный разбор экономики в статье по теме «Сколько стоит собственная платформа данных: считаем TCO Big Data-инфраструктуры».

Масштаб и цифры промышленного кластера?

Краткий ответ: Следующий шаг — несколько кластеров как одно логическое хранилище.

«Дижитрек» — не концепт, а контур в эксплуатации:

  • объём: более 1 ПБ в HDFS, прирост сырых данных около 200 ГБ в сутки;
  • 40 Data Nodes: 16 с SSD под Spark shuffle и temp, 24 с SATA под overflow;
  • узел: 96 vCPU, 756 ГБ RAM, 96 ТБ HDD;
  • поток: пик 15 000+ сообщений/с в Kafka;
  • 20+ млн файлов в HDFS, 500+ активных DAG, 100+ источников (ClickHouse, RDBMS, REST, файлы).

Рост — вертикальный (ресурсы на узле) и горизонтальный (новые Data Nodes без остановки сервиса).

Как устроена zero downtime?

Для скоринга, биллинга и телеметрии простой кластера недопустим. «Дижитрек» держит доступность на нескольких уровнях.

High Availability ключевых сервисов: HDFS NameNode (Active/Standby + JournalNodes), YARN ResourceManager, Hive Metastore на PostgreSQL + Patroni, ZooKeeper с нечётным кворумом.

Автоматизированный rolling restart: drain → exclude → ожидание завершения задач → рестарт → возврат → health-check. Для YARN NodeManager ждут numContainers=0, для HDFS DataNode — переход в IN_MAINTENANCE. Guardrails ограничивают число одновременных рестартов; pre/post-проверки идут по REST, JMX, VIP и портам. Restart_matrix строится по фактическим изменениям. Полный разбор процедур — в статье по теме «Как построить отказоустойчивую Big Data-платформу без простоя».

Эшелонированная безопасность?

Краткий ответ: Ключевые варианты: сеть: выделенный сегмент, VLAN, файрвол;, платформа: ALD PRO и Keycloak уже в проде, Vault для секретов, данные: Kerberos, Ranger, Knox, поставка: Nexus для артефактов, Bitbucket для ревью, Ansible против дрейфа конфигурации..

  • сеть: выделенный сегмент, VLAN, файрвол;
  • платформа: ALD PRO и Keycloak уже в проде, Vault для секретов — в плане CI/CD;
  • данные: Kerberos, Ranger, Knox — разграничение до таблиц и столбцов плюс аудит;
  • поставка: Nexus для артефактов, Bitbucket для ревью, Ansible против дрейфа конфигурации.

Платформа стыкуется с внешними OIDC-провайдерами под корпоративную политику идентичностей.

Data Science и MLOps на одной платформе?

Краткий ответ: Практическая связка DataOps и MLOps — в статье по теме «MLOps начинается с DataOps: почему без управления данными нельзя построить промышленный AI»; требования к AI-ready контуру — в «AI-ready Data Platform: какая инфраструктура нужна для корпоративного AI».

Мультиверсионность позволяет исследователю брать свежие библиотеки, а инженеру — не ломать прод. JupyterHub сокращает путь «тетрадка → Spark-джоба». Delta Lake даёт time travel: воспроизвести срез, на котором училась модель. Kafka и Debezium кормят обучение почти без задержки батча. dbt и Airflow делают трансформации тестируемыми.

В Q2 2027 — OpenMetadata + Spline для каталога и lineage, свой плагин качества данных. Так закрывается контур MLOps: от инженерии данных до наблюдаемости входа модели.

Как устроена поставка?

В комплект входят бинарники, собранные под Astra Linux; Ansible-роли полного цикла; smoke-тесты совместимости; автоматизация SRE (rolling restart, health-check, guardrails); документация по архитектуре, эксплуатации и авариям; поддержка и консультации по оптимизации. Промышленный кластер поднимается за дни, а не месяцы — без типичных конфликтов версий «соберите Hadoop сами». Это одна из причин, почему TCO открытого on-prem на горизонте 3–5 лет обычно ниже проприетарного облака (статья по теме — «Сколько стоит собственная платформа данных: считаем TCO Big Data-инфраструктуры»).

Дорожная карта 2026–2027?

Краткий ответ: Ключевые варианты: Q4 2026: CI/CD (Bamboo, Bitbucket, Nexus, Vault), кербероизация (Kerberos, Knox, RBAC), Airflow 3.1, OIDC для всех веб, Q1 2027: своя система управления кластером (GUI/API) вместо чистого Ansible., Q2 2027: OpenMetadata и Spline, плагин качества, Greenplum/Cloudberry, каталог на HMS и Iceberg., Q3 2027: пакет документации и заявка в Реестр российского ПО..

  • Q4 2026: CI/CD (Bamboo, Bitbucket, Nexus, Vault), кербероизация (Kerberos, Knox, RBAC), Airflow 3.1, OIDC для всех веб-UI.
  • Q1 2027: своя система управления кластером (GUI/API) вместо чистого Ansible.
  • Q2 2027: OpenMetadata и Spline, плагин качества, Greenplum/Cloudberry, каталог на HMS и Iceberg.
  • Q3 2027: пакет документации и заявка в Реестр российского ПО.

Критерии, по которым этот roadmap стоит сверять с тендером, собраны в статье по теме «Как выбрать Big Data Platform для крупного предприятия: 15 критериев оценки».

Чем это отличается от проприетарных стеков?

В отличие от частично открытых дистрибутивов и облачных data-platform, «Дижитрек» даёт полный исходник, отсутствие vendor lock-in, нативную Astra Linux, Delta Lake, мультиверсионность compute, автоматизированный rolling restart, CDC через Debezium и прозрачную цену без платы «за лишний узел». Сравнение клетки вендора и открытого формата Parquet/Delta — в статье по теме «Vendor Lock-in: сколько бизнес платит за зависимость от IT-вендора»; суверенитет кода и реестр — в «Open Source для Enterprise: почему открытый код становится вопросом цифрового суверенитета».

«Дижитрек» Big Data Platform — не «ещё один Hadoop». Это экосистема: петабайтное озеро, поток, мультиверсионный compute, аналитика и промышленная надёжность при полном суверенитете над данными. Компания может заниматься скорингом и отчётностью, а не борьбой со стеком.

Политика конфиденциальности

1. Общие положения

Настоящая политика обработки персональных данных составлена в соответствии с требованиями Федерального закона от 27.07.2006. №152-ФЗ «О персональных данных» и определяет порядок обработки персональных данных и меры по обеспечению безопасности персональных данных ООО "ДТ".

2. Цели обработки персональных данных

Персональные данные обрабатываются в следующих целях:

  • Обработка заявок и обращений пользователей
  • Предоставление информации о продуктах и услугах компании
  • Связь с пользователями по вопросам сотрудничества

3. Категории обрабатываемых персональных данных

Мы обрабатываем следующие категории персональных данных:

  • Фамилия, имя, отчество
  • Адрес электронной почты
  • Номер телефона
  • Информация, содержащаяся в сообщениях пользователей

4. Сроки обработки персональных данных

Персональные данные обрабатываются в течение срока, необходимого для достижения целей обработки, но не более 3 лет с момента последнего взаимодействия с пользователем.

5. Меры по обеспечению безопасности персональных данных

Мы принимаем необходимые правовые, организационные и технические меры для защиты персональных данных от неправомерного или случайного доступа к ним, уничтожения, изменения, блокирования, копирования, предоставления, распространения персональных данных, а также от иных неправомерных действий в отношении персональных данных.

6. Права субъекта персональных данных

Вы имеете право:

  • Получать информацию об обработке ваших персональных данных
  • Требовать уточнения, блокирования или уничтожения персональных данных
  • Отзывать согласие на обработку персональных данных
  • Обращаться с жалобами в уполномоченный орган по защите прав субъектов персональных данных

По всем вопросам, связанным с обработкой персональных данных, вы можете обратиться по адресу: privacy@digitrack.com
